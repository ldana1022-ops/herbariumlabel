# Backend, security and storage hardening for production

## What I checked first (current real state)

- The site is already on a real managed Postgres database (Lovable Cloud), not mock data or browser storage. All 41 herbarium records live there, plus users, roles, permissions, requests, prints, notifications and the activity log.
- Database size today: 13 MB. Images: 10 files, 49 MB total (about 5 MB per photo, stored as uploaded — no compression).
- Serial numbers are generated by a database counter and protected by a uniqueness rule, and the counter never reuses a number after a deletion. Accession number is kept in sync automatically.
- Row Level Security is on with per-role policies for every table; guests can only read a limited public view of specimens.
- Real gaps found: the specimen list downloads every record at once, several frequently filtered/joined columns have no index, coordinates and dates have no validation rules, login/logout is not written to the audit log, the image bucket accepts any file type and any signed-in user can overwrite or delete any image, and public scan endpoints have no abuse throttling.

Nothing below deletes or rewrites existing records. Data changes are limited to adding indexes, constraints and columns, plus optional generation of image thumbnails.

## 1. Data integrity and schema (database migration)

- Validation checks: latitude -90..90, longitude -180..180, altitude within a sane range, non-empty scientific name, collection/determination dates not in the future, request due date not before creation.
- Foreign-key and lookup indexes: `herbarium_specimens (status, created_by, collection_date, updated_at)`, `requests (assigned_to, created_by, specimen_id, status)`, `activity_log (actor_id, record_id)`, `notifications (read_at)`, `specimen_access (user_id)`.
- Text-search indexes (trigram) on scientific name, local name, Arabic local name, locality and collectors so search stays fast at 100k rows.
- Keep every existing unique constraint; add one on `specimen_prints.specimen_id` if any duplicate path exists.
- Concurrency: status and field updates move to conditional updates so two people editing the same record cannot silently overwrite each other; the second one gets a "record changed, reload" message.

## 2. Access control and audit

- Roles stay as they are (System Administrator / Editor / Viewer with per-action permissions) — enforced in the database, not the interface.
- Storage rules tightened: only the record owner or an administrator can replace or delete a specimen photo; everyone signed in can view. The bucket is restricted to JPG, PNG and WebP with a 10 MB cap.
- Audit log gains login and logout events, plus label printing and permission changes (some already logged). Log entries remain admin-only and unmodifiable by normal users.
- Public scan endpoints get simple throttling per visitor so the barcode lookup cannot be hammered, and they keep returning only the safe public fields.
- Re-verify that no key or secret appears in browser code (only the public project key, which is designed to be public) and that admin-only work runs behind server-side role checks.

## 3. Performance and scalability

- Specimen list switches to server-side paging, sorting, filtering and searching (page size 50) instead of loading the whole table; bulk actions operate on the current selection or the whole filtered set via the database.
- Dashboard counters move to database count queries instead of counting rows in the browser.
- Images load lazily and use a generated small preview for lists; the full image is only fetched on the detail, label and public pages.

## 4. Storage plan and estimates

Current photos average about 5 MB. That does not scale:

| Samples | At 5 MB/photo (today) | After compression (~400 KB + 40 KB thumb) |
| --- | --- | --- |
| 1,000 | ~5 GB | ~0.45 GB |
| 10,000 | ~50 GB | ~4.4 GB |
| 50,000 | ~250 GB | ~22 GB |
| 100,000 | ~500 GB | ~44 GB |

Row data itself is small: roughly 1.5 KB per specimen plus logs, so 100,000 samples is well under 1 GB of database space.

Plan: compress and resize photos in the browser before upload (long edge 2000 px, WebP/JPEG quality ~82) and store a thumbnail alongside. Existing photos are left untouched; a one-time optional re-compression can be run later on request.

## 5. Backup and recovery

I will document, and verify where visible, the managed backup setup: automatic daily database backups with point-in-time restore handled by the platform, restore performed from the backend settings, and file storage kept separately from the database. Anything that must be arranged outside the platform (for example longer retention or an off-platform copy of images) will be stated plainly in the final report.

## 6. Final report

At the end you get a written report covering: database provider and configuration, schema, sign-in method, roles and permissions, access policies, storage capacity and growth estimates, backup/restore, issues found and fixed, remaining risks, and the exact pre-launch steps.

## Verification before I call it done

Create/edit/delete/search/filter/status changes against the real database, refresh and re-login persistence, two simultaneous sessions, guest scan access limited to public fields, attempts to reach admin functions as a normal user (must fail at the database), and a synthetic large-dataset check that paging holds up. Existing 41 records confirmed unchanged.

## Technical notes

Postgres migration for constraints/indexes; optimistic-concurrency guards via `updated_at` predicates; paged reads through `range()` with `count: 'exact'`; storage policies rewritten against `private.is_super_admin` / owner path prefix; bucket `allowed_mime_types` set; login/logout logging through the existing `private.log_activity`; public-endpoint throttle keyed by IP hash in a small table with a cleanup rule.
